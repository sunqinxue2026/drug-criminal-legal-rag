# 数据库与检索设计文档

## 1. 当前实现概览

当前项目采用“`MySQL + FAISS`”作为默认落地方案：

- `MySQL` 负责业务数据、法律知识元数据、法律文书元数据与分块结果存储
- `FAISS` 负责本地向量索引
- Flask 侧额外实现了轻量词法召回与混合重排，不再是“只靠单一路径向量检索”
- 代码中保留了 `Milvus` 兼容封装，但当前默认运行链路并不依赖 `Milvus`

因此，旧版本文档中“本项目采用 FAISS（开发）+ Milvus（生产）”的表述已经不准确；更准确的说法应为：

> 当前仓库默认使用 MySQL + FAISS，本地即可运行；Milvus 兼容代码属于可扩展方向，而非当前默认部署前提。

## 3. 关键字段设计

### 3.1 `legal_knowledge`

该表用于保存“可直接进入 RAG 检索”的规范知识主记录，核心字段包括：

- 来源字段：`source_type`、`source_name`、`source_url`、`source_reliability`
- 规范属性：`knowledge_type`、`knowledge_subtype`、`document_name`、`document_level`
- 发布信息：`issuer`、`effective_date`、`expiry_date`、`current_status`
- 主题信息：`business_domain`、`topic`、`chapter_title`、`section_title`
- 条文信息：`article_number`、`article_title`
- 检索文本：`summary`、`display_text`、`retrieval_text`

这套字段设计支撑了前端“引用来源可核验”的展示能力，也支撑了论文中的“规范知识结构化导入”描述。

### 3.2 `legal_document`

该表用于保存结构化文书元数据，核心字段包括：

- 来源与文件信息：`source_name`、`source_url`、`source_file_name`、`file_sha256`
- 文书识别信息：`title`、`case_number`、`court_name`、`court_level`
- 分类信息：`document_type`、`document_subtype`、`case_type`
- 领域信息：`business_domain`、`procedure_domain`
- 结果信息：`decision_result`、`decision_date`、`effective_date`
- 摘要信息：`facts_summary`、`issues_summary`、`reasoning_summary`、`result_summary`
- 检索文本：`summary`、`retrieval_text`、`display_text`、`raw_text`、`clean_text`

### 3.3 分块表

`legal_document_chunk` 与 `legal_knowledge_chunk` 都采用类似的结构：

- 切块策略：`chunk_strategy`、`chunk_version`
- 结构定位：`section_type`、`section_title`、`header_path`
- 检索角色：`retrieval_role`
- 权重与顺序：`section_weight`、`section_order`、`chunk_index`
- 内容字段：`chunk_text`、`retrieval_text`
- 辅助字段：`char_count`、`token_count`、`metadata_json`

这意味着当前系统并不是简单把全文平均切段，而是保留了章节类型、角色和权重等检索语义。

## 4. 向量索引实现

### 4.1 当前默认向量后端

当前默认索引管理器为 Flask 侧的 [faiss_manager.py](/D:/CODE/RAG/web-flask/algo/vector/faiss_manager.py)：

- 默认索引类型：`faiss.IndexFlatIP`
- 预处理方式：向量写入和查询前统一做 `L2 normalize`
- 相似度语义：归一化后以内积近似余弦相似度
- 落盘文件：`*.index` + `*.meta`

### 4.2 向量维度

向量维度不再写死为 1024，而是由当前模型名推断：

- `bge-small-*`：默认 `512`
- `bge-base-*`：`768`
- `bge-large-*`：`1024`

当前仓库默认模型为 `BAAI/bge-small-zh-v1.5`，因此默认维度应按 `512` 理解，而不是旧文档中的 `1024`。

对应实现见 [bge_client.py](/D:/CODE/RAG/web-flask/algo/vector/bge_client.py)。

## 5. 检索链路

当前检索并非单一“向量召回 -> LLM”流程，而是更接近如下结构：

1. 对用户问题做领域分析、意图分析和风险识别
2. 生成扩展检索词与偏好分块角色
3. 从 `legal_knowledge_chunk`、`legal_document_chunk`、专题案例入口中构建候选集
4. 进行 FAISS 向量召回
5. 进行轻量词法召回
6. 使用混合分数做重排
7. 将高分块交给大模型生成结构化答案

相关实现见：

- [legal_query_analyzer.py](/D:/CODE/RAG/web-flask/algo/legal_query_analyzer.py)
- [legal_lexical_retriever.py](/D:/CODE/RAG/web-flask/algo/legal_lexical_retriever.py)
- [rag_engine.py](/D:/CODE/RAG/web-flask/algo/rag_engine.py)

## 6. 数据一致性与索引刷新

当前仓库没有把“定时凌晨同步”作为默认运行机制，现阶段更接近以下模式：

- 通过后台导入接口写入 `legal_knowledge` 或 `legal_document`
- 通过 `/item/reindex`、`/legal-knowledge/reindex`、`/legal-document/reindex` 主动刷新索引
- 导入接口可通过 `rebuildIndex=true` 在导入后直接重建

因此，旧版本文档中“每日 2 点自动同步”的描述不应直接用于论文或实现说明。

## 7. 论文中建议使用的表述

可在论文中表述为：

> 系统在数据层采用关系型数据库与本地向量索引的组合架构。MySQL 负责保存用户、会话、专题案例、规范知识、法律文书及其结构化分块信息；Flask 服务基于 BGE 向量模型生成语义表示，并使用 FAISS 维护本地向量索引。同时，系统引入轻量词法召回与混合重排机制，以提升涉毒刑事专题场景下的检索稳定性和引用可解释性。

## 8. 当前边界

- 当前默认部署路径是 `MySQL + FAISS`
- `Milvus` 兼容封装存在，但不应表述为当前必需依赖
- 当前默认嵌入模型为 `bge-small-zh-v1.5`
- 当前检索链路已包含词法召回与混合排序，不能再概括为“仅向量检索”
